# WP ability evals: agent guide

The `wp-ability-evals` package: evals for WordPress abilities, where real agents do site-owner tasks on a real site and the result is graded on what changed on the site. `README.md` shows the layout; this file covers what an agent needs on top when working on the package itself. A project that uses the package has its own guide, which starts as `template/AGENTS.md`.

Status: early. A scenario runs end to end with Claude Code or Codex on a wp-env site. Every check is built, with a judge for rubrics. A run is saved as a folder with the models and judges that ran (`models` in `run.json`), and `view` shows the saved runs in a browser, opening on an Overview of where the packs' abilities stand, counted from each scenario's latest verdict (`src/coverage/`), with a warning when verdicts mix models. Before every run the server checks read the site's MCP server with MCP Inspector (`--strict`), check listed abilities' definitions (schema portability, descriptions, `readOnlyHint` annotations), and decide which scenarios can be judged; `site check` does that alone (failing on error-severity definition problems too), and `validate` notes the abilities no scenario names. A project's hooks run at six fixed points of a run, and a site marks its start after the before-run hooks. A story file holds a story, its starting content and its scenarios. The `createGiven()` hook puts a scenario's starting content on the site through the entity types' writers, and the agent works only once the site was read and found to start as the scenario says. `verify` proves a scenario on a site without an agent: its starting content, its site check and its answer. `expect.site` can mark an item the agent creates (`$new`) and compare a text by what it contains (`$contains`). `expect.abilities` can name the arguments an ability must have run with, and `expect.forbidden` the abilities that must not run. A trial's page in the viewer shows what changed on the site and the site before, from the two readings in the trial's file. The first skill, `add-evals`, drives adding evals in a project; it was not yet tried on a fresh agent. `update` takes the installed package's skills and guide into a project that was made with an older version, and `validate` says when a project's copy differs.

Some parts have no automated test, because they need Docker, a signed-in agent or a browser. Check them by hand in a project after changing them:

- The wp-env site (`src/sites/wp-env.ts`): `site start`, `site state`, change the site, `site reset`, `site state` again, `site stop`. Do it with a before-run hook in the project's settings that creates a post through `site.wp`: the post must be there after the start and again after the reset, without the change. The site's MCP server must still answer with the saved sign-in after the reset. Stop only the site's WordPress container with `docker stop`: `site start` must start it again, and `site check` must then read the server. Try `site remove` only on a site of its own, with its own port, in a copy of a project. Add a site file with the port of a site that runs, and one with a port that a plain program holds: `site start` must stop on each with a message that names the port, what holds it and the site file, and start nothing. Remove the file and its folder under `.wp-ability-evals/sites/` afterwards.
- The server checks (`src/server-checks/`): `site check` on a wp-env site must say that the server presents every listed ability. Then list an ability in `pack.yaml` that the site does not have: `site check` must name it as missing and end with an error. Remove an ability of the site from `pack.yaml`: it must be named as a tool that no pack lists, and the command must end without an error. Register or expose a listed ability with a broken schema (e.g. a bare `true` schema), empty description, or contradictory `readOnlyHint`: `site check` must report the definition finding with severity, path, issue, and fix, and end with an error; a warning-severity schema finding alone must be printed without failing `site check`, and a `run` must still run trials and record `definitionFindings` in `run.json`. Add a `beforeRun` hook that stops the site's WordPress container (`docker stop`), so the server is gone once the site has started: `site check` must say the server could not be read, name its address and end with an error. Remove the hook afterwards: the next `site start` starts the container again. Inspector must leave nothing in `~/.mcp-inspector`: compare that folder's files and their times before and after. For a run, list an ability in `pack.yaml` that the site lacks, name it in a scenario's `expect.abilities`, and `run --filter` that scenario: it must end without starting an agent, so it spends nothing, with every trial "could not be judged" and the reason naming the ability; with `state: to-be-implemented` the trials must instead be "not built yet" and the scenario "failed as expected", and `site check` must call the ability not built yet and end without an error. `run.json` must hold `serverChecks`, and the trial's page in the viewer must show the reason.
- Starting content (the writers in `src/entities/`, `apply` in `src/sites/wp-env.ts`, `src/hooks/create-given.ts`, `src/hooks/start-trial.ts`): `verify --site local --no-judges` reaches them without an agent. Add a story file with `given` items and a scenario whose `expect.site` changes one of them: its `start` and `the change` lines must pass, and `site state` must then show each item under its key with its fields. Give one item a title with a quote, a `$` and a non-ASCII letter. For a post without a slug, create a draft with WP-CLI in the site's CLI container, find it as `#<ID>` in `site state`, and `apply` a change to that key from a script that calls the built package: the post must change, and no second post may appear. Run it again with no hooks in the settings, and with a `beforeTrial` hook that leaves an item nobody declared: the `start` line must fail with the differences. Then break the PHP of a project's entity type, one place at a time: a syntax error and a call to a function that does not exist in its reader must make `site state` name the type and the line in the reader, and a syntax error in its writer must make the `start` line of `verify` name the writer.
- `verify` (`src/verify/`): in a project, `verify --site local --no-judges` on a story file with `given` and scenarios that change, rename and remove a `given` item, which must pass every step. Then break one scenario at a time and read its line: an `expect.site` that already holds at the start (`no change` fails), one that names an item `given` does not create (`the change` fails or says what it created), a `reference` without a text of `contains`. The command must end with an error each time. A `contains` without a `reference` is no mistake: its line must say that it was not checked, and the last line must count it. For the operators of `expect.site` (`src/scenarios/operators.ts`, `src/checks/site.ts`, `changeToMake` in `src/verify/steps.ts`), add a scenario that expects a new draft through `$new` and a text through `$contains`: it must pass every step, and when it was the last scenario proved, `site state` shows the draft under its label. Then break it: a label that is the key of an item the site starts with, and two items marked `$new` with the same fields, must each fail `the change` with a line that names them. Remove the story file afterwards if the project has no ability for it. Never run it without `--no-judges` unless asked: grading spends the user's plan.
- The hooks of a run (`src/hooks/`, `src/runner/`, `src/verify/`): `site start` runs the before-run hooks, so a hook that throws there shows how a failure reads and that the after-run hooks still ran. `verify --no-judges` runs the hooks of every point without an agent: name a hook at each point that notes that it ran, and read the order; make one throw at each point, and read how the failure shows. In a run, the points around a scenario and a trial need an agent, which spends the user's plan, so ask first.
- An agent adapter (`src/agents/`): one `run` with the agent, then read the trial's file in the run's folder under `results/`. Its session must list only the site's MCP tools and the agent's tool search, and none of the user's skills, plugins or MCP servers. This spends the user's plan, so ask first.
- A judge (`src/judge/`): grade a right and a wrong answer with it, and read both verdicts. `verify --filter <a scenario with a rubric>` without `--no-judges` does that with every judge in the settings. This spends the user's plan too.
- The viewer's page (`viewer/`): `npm run build`, then `view` in a project that has saved runs. Open the list of runs, one run and one trial, and look at the browser's console for errors. The page loads once, so reload it after a build. For the site in a trial's page, open a trial whose file has `site` and one whose file has none: the first shows what changed and, once unfolded, the site before, and the second shows neither. Where no saved trial has `site`, copy a run's folder in `results/`, add `site` with two readings to one of its trial files by hand, in the shape `site state` prints, and delete the copy afterwards. For the Overview (`viewer/overview-page.tsx`, `src/coverage/`), the page opens on it: check the headline, the pack's bar and legend, Needs attention, Asked for not built yet, the map's hover line and the panel a square opens, the table's search and a filter on where an ability stands, the panel a row opens, and a scenario's link to its run. Where the saved runs have no failing scenario or the packs no `to-be-implemented` one, copy the newest run's folder under a later time, set `startedAt` in its `run.json` and make one verdict `fail` and one tool call of a trial `isError`, add a `to-be-implemented` story file, and remove both afterwards. For the site and the packs, give that copy `serverChecks` with an ability in `missing` that a pack lists and no scenario names, one that only the `to-be-implemented` scenario names, and a tool in `inNoPack`, and keep only one scenario's verdict and trials in it, as `--filter` would: the first shows as missing on the map and in its own list, the second as not built yet, the tool under "in no pack", and the trend has one point per run without dropping the scenarios the copy left out. Start it on a port of its own, such as `view --port 4420`, so that the user's own viewer keeps running. A build still changes the page theirs serves, and a server started before a change in `src/viewer/` answers the new page with errors, so tell them to restart it.
- `update` and the notice of `validate` (`src/init/update.ts`, `src/cli/main.ts`): in a project, change a line of a skill in `.agents/skills/` and one of the guide in `AGENTS.md`, and add a line of the project's own above the guide. `validate` must name both files as changed in the project, `update` must name them and write nothing, `update --overwrite` must list both as updated and leave the added line, and a second `update` must find nothing. Then remove the two marker lines from a copy of the project: `update` must end with an error that says what to do, and write nothing.
- Codex does not report its tools in a run. `codex debug prompt-input` with the adapter's `--disable` and `--config` options prints the tools and messages the model would get, without a model call. Run it with `HOME` set to an empty folder, as the adapter does.

## Build, test and lint

- Install and build: `npm install`
- Types: `npm run typecheck`
- Tests: `npm test` (builds first, because one test runs the built command the way a project does)
- Build: `npm run build`
- Run from source: `npm run evals -- --help`

## Conventions

- Use the words `CONTEXT.md` defines, in code, comments and output.
- A project must never need a change in this package. If adding an agent, an entity type or a kind of site would mean editing `src/`, the extension points in `src/config/types.ts` are missing something: fix that instead.
- `src/index.ts` is everything a project may import. Changing it changes what projects depend on.
- Agents are the main users of this package. Write error messages and command output so that an agent can act on them: say what is wrong, where, and what to do.
- A file a project writes is validated when it is loaded, by a `validate.ts` next to its `types.ts`. A new field needs both: the type, and a rule with a message that says what to write. Loading collects every problem (`InvalidProjectError`) instead of stopping at the first.
- Node runs the TypeScript in `src/` directly during development. Imports name the `.ts` file, type imports use `import type`, and only erasable syntax is allowed: no enums, namespaces or constructor parameter properties. Projects run the built `dist/`, because Node does not run TypeScript from an installed package.
- Each folder in `src/` owns one thing, and its `types.ts` is its contract. Dependencies point one way: `cli` uses `runner` and `verify`, each of those uses everything else but not the other, and nothing uses `runner`, `verify` or `cli`.
- Packs are plain data. Code that reads or changes a site is in `src/`, or in a project's `extensions/`.
- The framework fixes the points of a run, and a project's hooks do the work at them. What prepares or cleans up a site for one project is a hook in that project, never a step in the runner. The framework decides what a failing hook means, and every failure names the point and the hook (`hooks/run.ts`).
- A site has a clean state, as it was set up, and a marked start. `start()` returns to the clean state and forgets the marked start, `markStart()` marks the site as it is, and `reset()` returns to the marked start. "Start the site, run the before-run hooks, mark the start" is `startRunOn` in `hooks/run-on-site.ts`. `run`, `verify` and `site start` all call it, and so must anything else that starts a site for scenarios. What works on the started site is handed to `endRunOn` there, as `run` and `verify` do: the after-run hooks then run whatever happens, and a failure of the work is thrown with what went wrong in them, never in its place.
- A trial starts on a site in one way too: `startTrial` in `hooks/start-trial.ts` resets the site, runs the before-trial hooks, reads the site and compares it with its marked start plus the scenario's `given`. `run` and `verify` call it, and so must anything else that prepares a site for a scenario. What it compares with is the site as read once, right after `startRunOn`. A `SiteNotResetError` from it means the before-trial hooks were not reached; after any other failure the after-trial hooks are still owed.
- `verify` proves a scenario with what a run uses, and with nothing made up: `startRunOn` and `endRunOn` around it, `startTrial` to prepare the site, `Site.apply` in the agent's place, the site check a trial gets (`siteCheckOf` in `checks/site.ts`), and the project's hooks at every point. It has no transcript, so it gives none to a hook or a check. What each step decides is a pure function in `verify/steps.ts`, tested with plain values, and the calls to a site or a judge around it stay thin. A new thing a scenario can expect needs a step there, or a plain line in the output that says it is not covered, as `expect.abilities` and `expect.forbidden` have.
- A step of `verify` fails only when it shows the scenario to be wrong. What stops a step from outside, such as a hook that failed, a site that did not answer or a judge that gave no verdict, makes it "could not be checked". Both end the command with an error. A step that is left out is `skipped`, as the grading is with `--no-judges` and `contains` without a `reference`: its line says why, the last line counts it, and it ends nothing.
- Starting content is data, and nothing creates it behind the scenes. `createGiven()` is a hook like a project's own, and a project may replace it. The comparison before the agent works is the framework's, and no hook can switch it off.
- An entity type's writer and its reader agree on the key: what a writer creates under a key, the reader reports under that key. Where a reader makes up a key for an item that has none of its own, as `posts` does with `#<ID>` for a post without a slug, the writer finds the item by that key and refuses to create one under it. A change reaches a site as data, never as text pasted into code: on a wp-env site the writers' PHP reads it as JSON from its input (`changeWith` in `sites/wp-env.ts`).
- Scenarios name abilities and site changes, never MCP tools and never checks.
- A key that starts with `$` in `expect.site` is an operator, never a field or a plain value. There are two. `$new: true` marks an item the agent should create where the site chooses its key: the item's key in the file is then a label, and the item is found by its fields. `{ $contains: [texts] }` as a field's value compares the field by the texts it contains. A key without `$new` is always looked for on the site, so a mistyped key stays "expected, but not found".

  ```yaml
  expect:
    site:
      posts:
        sale-announcement: { $new: true, status: draft, title: Summer sale } # a label: the site chooses the key
        summer-sale: { content: { $contains: ['20%', 'July'] } }
  ```
- Only `scenarios/operators.ts` tells an operator from a plain value. The rules of a story file, the site check and `verify` ask it. `given` and a change handed to `Site.apply` hold plain values only: `verify` turns `expect.site` into such a change first (`changeToMake` in `verify/steps.ts`). A new operator needs its type, its rule in `scenarios/validate.ts`, its part in the site check, and what `verify` makes of it.
- A check on abilities says what ran, never how the agent got there. `expect.abilities` asks that an ability ran at least once without an error, in one call with every argument the scenario names for it; `expect.forbidden` asks that an ability did not run at all, where a call that failed counts. Elsewhere a call that came back with an error changed nothing and is no mistake: `no-writes` and `known-abilities` count only calls that ran without an error, and only `forbidden` and a `none` scenario count a refused try. Neither the order of the calls nor their number is checked, and no check may be added that does: an agent may take a valid path the scenario's author did not expect.

  ```yaml
  expect:
    abilities:
      - core/content-query
      - core/content-update: { status: publish }
      - core/content-query: { status: [draft, pending] } # a list: one of these values
    forbidden: [core/content-delete]
  ```
- Only `scenarios/abilities.ts` tells the two forms of an entry of `expect.abilities` apart: a name, or that one name mapped to arguments. The rules of a story file, the cross-checks and the check ask it. An argument is compared as the site check compares a plain value (`same` in `checks/site.ts`), and a list in the scenario means one of its values. In `same` a number matches its text, and nothing else matches a value of another type: `true` is not met by `1`. So an argument whose own value is a list or a mapping can't be expected, and `scenarios/validate.ts` says so: do not add syntax for it without a scenario that needs it.
- Only `checks/abilities.ts` knows where a tool call holds an ability's input. Where an ability is a tool, it is the tool's input. Where a tool runs any ability, it is the argument that the tool's entry in `runTools` of the server's `LookupTools` names as `inputArgument`, next to `nameArgument`. A server may have several such tools, and each names its arguments in its own way. Take such a name from a saved trial or from the server's own tool list, never from memory: the MCP Adapter's is `parameters`.
- The reason of a failed check on abilities names the ability, the arguments that were expected and what each of its runs had for them, so that an agent can tell a wrong argument from an ability that did not run.
- The site check never guesses which created item a label means (`newItems` in `checks/site.ts`). Each label is decided on its own, against every created item: exactly one must fit, and a created item stands for one label only. Anything else fails with a reason that names the label and the items.
- A file in a pack's `scenarios/` folder is a story file: one story in a person's words, then the scenarios made from it, which are data. `given` is starting content, at the story for all its scenarios and at a scenario for that one. Loading joins the two (`scenarios/load.ts`), so a `Scenario` in code carries its full starting content, and only a pack's `stories` say which story a scenario belongs to.

  ```yaml
  story: |
    As a site owner I want to publish a draft by asking for it.
  given: # optional
    posts:
      summer-sale: { title: Summer sale, status: draft }
  scenarios: # may be empty or left out while the story waits
    - id: content/publish-a-draft/by-its-topic
      request: Publish my draft about the summer sale.
      kind: write
      given: # optional, added to the story's; the same item at both levels is a problem
        posts:
          winter-sale: { title: Winter sale, status: draft }
      expect:
        site:
          posts:
            summer-sale: { status: publish }
  ```
- An agent under test runs as a first-time user: signed in, in an empty folder outside any repository, with none of the user's settings, rules, skills or memory. Nothing it can see may say it is an evaluation: not the request, seeded content, the MCP server's name or a folder name.
- Every file starts with a comment that says what it is for and why it exists.
- `wp-plugins/` holds the WordPress plugins that come with the package, for a site file to name under `wpEnv.plugins`. A plugin is on the site an agent works on, so its name and texts say nothing about evals. After changing one, check it on a real site: `site start`, then list the MCP server's tools.
- `viewer/` is the page the `view` command serves, and the one place with browser code. It is written with React and the WordPress design system: `@wordpress/dataviews` for tables, `@wordpress/ui` for the rest, `@wordpress/components` only where those two have nothing. `@wordpress/ui` is still experimental, so its version is pinned; read the component's types in `node_modules` before using one. The page takes the shape of its data from `src/results/types.ts` and imports nothing else from `src/`: that file re-exports, as types, what a trial's file is made of, so a type the page needs from another part is added there. It shows what a trial's file holds and decides nothing: `viewer/site-changes.ts` works out what differs between a trial's two readings of the site, for a person to read, and whether that is the change the scenario expects stays the site check's. It is plain code, tested in `test/site-changes.test.ts`. `scripts/build-viewer.mjs` bundles it with esbuild into `dist/viewer/page/`.
- `template/` is what `init` copies. A change there needs the file list in `test/init.test.ts` updated.
- `template/AGENTS.md` holds the guide between two marker lines, `<!-- BEGIN wp-ability-evals guide ... -->` and `<!-- END wp-ability-evals guide -->`. `update` replaces what a project has between them, so what every project needs goes inside. What is outside them is copied once and is the project's from then on: a change there never reaches an existing project. Projects hold the two lines, so never change how they read (`test/update.test.ts` writes them out for that reason).
- The guide is split. `template/AGENTS.md` keeps what every session needs: the commands, where things are, the rules, and one line for each file of `guide/` that names the work it is read before. `guide/` holds the rest, one file per topic, which `init` copies into a project's `.agents/guide/` and `update` copies again. A new topic file needs its line in the map and in the file list of `test/init.test.ts`; a fix to a topic goes in its file, never in `template/AGENTS.md`.
- `skills/` holds the skills `init` copies into a project's `.agents/skills/` and links from its `.claude/skills/`, and `update` copies again. Every skill names `.agents/rules/<its name>.md` near its top as the place for a project's own rules and tells the agent to read it first, so that a project never has a reason to change its copy. `update` replaces a copy that is still what the package copied, and stops at one that was changed in the project: `src/init/record.ts` keeps the record that tells the two apart, and its format can't change, because projects hold it. A skill holds the order of a job and the judgment in it. The commands stay in `template/AGENTS.md`, and the formats and what the output means in `guide/`. A skill points to a topic file by its path: after renaming a file in `guide/`, or changing a command or a field, search `skills/` and `template/AGENTS.md` for it. `skills/README.md` says what goes in a skill.

## Safety

- Do not read or commit `.env` files.
- A live run spends the user's agent plan or API credit. Start one only when asked.
- `verify` calls a model only to grade the answers next to a rubric, which spends each judge's plan or API credit. Run it with `--no-judges` unless asked for the grading.
